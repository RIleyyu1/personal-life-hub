# 个人健康生活助手 · 设计文档 v0.1

> 状态：v0.1 已确认，第一阶段（MVP）开发中。

## 1. 目标

一个只为我自己定制的生活网站（手机优先），用最少的手动输入完成：

- **吃**：拍照记录每一餐，估算热量与营养素
- **练**：记录每次训练的动作，估算能量消耗，追踪进步
- **算**：根据个人参数计算每日消耗与营养目标，并随真实数据自动校准
- **建议**：基于当天/本周的数据给出可执行的饮食与训练建议

## 2. 原始需求（初稿）

| # | 需求 |
|---|------|
| R1 | 每天上传照片，只通过拍照记录每顿饭的大概卡路里 |
| R2 | 记录每天健身的每个动作及消耗的能量 |
| R3 | 各种建议 |
| R4 | 个人参数 → 每日消耗与各类营养素的摄入目标 |

## 3. 建议补充的内容

按重要程度排序。★ = 强烈建议放进第一版。

### 3.1 ★ 体重趋势 + 自适应 TDEE 校准（最重要的补充）

- 拍照估算热量误差通常在 ±20–30%（看不见的油、酱汁、份量），运动手环/公式估算的运动消耗也普遍偏高。
- 如果只靠"估算摄入 − 估算消耗"，误差会叠加，结论不可靠。
- 解决方法：每天早上称重 → 取 7 天移动平均 → 结合记录的摄入，**反推真实 TDEE**（每 1 kg 体重变化 ≈ 7700 kcal）。
- 这样即使拍照估算有系统性偏差，目标热量也会被自动修正。这是整个系统"越用越准"的核心。

### 3.2 ★ 拍照识别的"可修正"设计

- AI 识别结果以**区间 + 置信度**展示（如 "650 kcal，范围 520–780"）。
- 一键修正：份量滑块（½ / 1 / 1.5 / 2 份）、增删食物、标记"油多/少油"。
- 记住修正：常吃的菜、食堂/常去餐厅的菜会越来越准。
- 快捷记录：常吃组合一键复用（比如固定早餐），不必每次拍照。
- 拍照小技巧提示：俯拍 + 放一个参照物（手、筷子、标准碗）提高份量估算准度。
- 可选：条形码扫描包装食品（精确值）。

### 3.3 ★ 训练记录要"追进步"，不只算热量

- 动作库（按肌群分类）、组数、次数、重量、RPE/主观强度。
- 能量消耗：有氧用 MET × 体重 × 时长；力量训练的热量估算本身很粗，**如实标注为估算**。
- 更有价值的指标：渐进超负荷（重量/容量曲线）、个人纪录 PR、每周各肌群训练量。
- 训练模板 / 计划（如 推-拉-腿），打开即可按模板记录。

### 3.4 ★ 每日仪表盘

- 热量：目标 / 已摄入 / 剩余，训练消耗单独展示。
- 三大营养素进度环：蛋白质、碳水、脂肪。
- 次要指标：膳食纤维、饮水、钠。
- 一句话建议："还差 45 g 蛋白质，晚餐可以加一份鸡胸/豆腐"。

### 3.5 建议引擎

- **规则层**（稳定、可解释）：蛋白质不足、连续 3 天热量过低、某肌群一周未练、体重下降过快等。
- **AI 层**（每日/每周总结）：读取当天数据，生成下一餐建议、训练调整建议。
- **安全边界**：热量目标不低于安全下限、减重速度不超过每周体重的 1%；不做医疗诊断。

### 3.6 恢复与生活状态

- 睡眠时长/质量、每日步数、精力/心情打分（1–5）。
- 用途：解释训练表现与体重波动（睡眠差、高盐 → 水分波动），让建议更准。

### 3.7 身体变化记录

- 体脂率（可选）、腰围/臀围/臂围等围度。
- 进度照片（仅自己可见），可按月并排对比。

### 3.8 周报 / 月报

- 平均摄入 vs 目标、体重趋势、校准后的真实 TDEE、训练量变化、PR、达标天数。
- 下周目标自动调整建议。

### 3.9 数据接入（后期）

- Apple 健康 / Garmin / 小米等：步数、心率、睡眠、训练消耗（避免重复录入）。
- 智能体重秤数据导入。

### 3.10 其他

- 提醒：该记录午饭了、该喝水了、该称重了。
- 数据导出（CSV/JSON），数据完全归自己所有。
- 隐私：照片与身体数据只存在自己的存储里，账号单人登录。

## 4. 核心计算

### 4.1 基础代谢 BMR

- 默认 Mifflin-St Jeor：
  - 男：`10 × 体重kg + 6.25 × 身高cm − 5 × 年龄 + 5`
  - 女：`10 × 体重kg + 6.25 × 身高cm − 5 × 年龄 − 161`
- 如有可靠体脂率，改用 Katch-McArdle：`370 + 21.6 × 去脂体重kg`

### 4.2 每日总消耗 TDEE

- 初始值：`BMR × 活动系数`（久坐 1.2 / 轻度 1.375 / 中度 1.55 / 高 1.725）
- 两周后：用体重趋势 + 摄入记录自适应校准（见 3.1），逐步取代公式值。

### 4.3 目标热量与营养素

| 目标 | 热量 |
|------|------|
| 减脂 | TDEE − 300~500 kcal（或每周减体重 0.5–1%） |
| 维持 | TDEE |
| 增肌 | TDEE + 200~300 kcal |

- 蛋白质：1.6–2.2 g/kg 体重
- 脂肪：0.6–1.0 g/kg 体重（不低于总热量的 20%）
- 碳水：剩余热量
- 膳食纤维：约 14 g / 1000 kcal
- 饮水：约 30–35 ml/kg，训练日增加

## 5. 技术方案

**当前（第一阶段，本地运行）**

| 部分 | 选择 | 理由 |
|------|------|------|
| 形态 | 响应式网站 + PWA 清单 | 同一地址按设备分工：触屏设备进入记录界面，鼠标设备进入只读总览；手机可"添加到主屏幕"；相机通过 `<input capture>` 调用 |
| 后端 | Node.js 22 内置 `http` + `node:sqlite` | 零构建、零数据库服务，`npm start` 即可运行 |
| 前端 | 原生 JS（ES Modules） | 无构建步骤，改完刷新即可 |
| 食物识别 | Claude 视觉模型（结构化 JSON 输出） | 无 key 时自动进入演示模式 |
| 存储 | `data/` 下的 SQLite 与照片文件 | 数据只在自己电脑上 |

**以后（上线时再考虑）**：用户希望在外随时可用、不依赖本地部署。届时需要：托管的数据库和照片存储（如 Postgres/Supabase）、登录（目前没有任何鉴权，只适合家里 Wi-Fi）、HTTPS；前端复杂后可迁到 React/Next.js。

## 6. 数据模型（草案）

```
profile        身高、性别、出生日期、活动水平、目标、目标速度
body_log       日期、体重、体脂、围度、进度照片
meal           时间、餐次(早/午/晚/加餐)、照片、总热量、蛋白/碳水/脂肪、置信度
meal_item      所属餐、食物名、份量(g)、热量、营养素、是否被手动修正
food_memory    常吃食物/组合 及其修正后的营养值
workout        日期、时长、类型、估算消耗、主观强度
workout_set    所属训练、动作、组序、次数、重量、RPE
exercise       动作库：名称、主肌群、MET 值
daily_status   日期、睡眠、步数、饮水、精力/心情
daily_target   日期、目标热量与营养素、当日 TDEE 估计
suggestion     日期、类型、内容、来源(规则/AI)
```

## 7. 开发路线

### 第一阶段 · MVP（能每天用起来）

1. 个人档案 + BMR/TDEE/营养目标计算
2. 拍照记餐：上传 → AI 识别 → 修正 → 保存
3. 训练记录：动作库 + 组/次/重量 + 消耗估算
4. 每日体重记录
5. 每日仪表盘
6. 电脑端只读数据总览；体重和训练重量支持 kg / lb 切换（2026-09-27 追加）

### 第二阶段 · 变聪明

7. 自适应 TDEE 校准
8. 规则建议 + AI 每日总结
9. 常吃食物记忆与一键复用
10. 训练 PR、肌群训练量统计
11. 周报

### 第三阶段 · 更完整

12. 睡眠/步数/心情记录
13. 进度照片、围度
14. 健康数据导入（Apple 健康等）
15. 提醒、数据导出
16. 云端部署：在外随时可用，不依赖本地运行（用户已提出，排在后面考虑）

## 8. 已确认的决策（2026-09-27）

| 问题 | 决定 |
|------|------|
| 使用设备 | 手机和网页都要能用 |
| 部署 | 先在本地运行看效果 |
| 目标 | 会动态变化：支持减脂 / 维持 / 增肌 / 重组，随时切换并保留历史 |
| 设备依赖 | 只依赖每日称重；手表容易忘戴，不作为长期依赖项 |
| 饮食记录 | 饮食多元，只通过拍照记录；可补充调料，修正与调料形成长期记忆 |
| 界面语言 | 中文（未单独确认，按对话语言默认） |
| 设备分工（第二轮） | 手机负责每天的记录和各项功能；电脑网页不负责记录，也不负责功能操作。电脑端具体展示哪些内容，用户原话在转写中缺失，目前按"只读数据总览"实现，待用户确认 |
| 体重单位（第二轮） | 除 kg 外增加 lb 切换；实现时训练重量也跟随同一设置 |
| 部署（第二轮） | 希望在外随时可用、不依赖本地部署；用户明确排在后面考虑，当前仍本地运行 |
